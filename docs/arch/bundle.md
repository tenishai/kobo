# bundle — the daedalus agent bundle kobo writes into each agent repo

The vendored schema is daedalus v0.5.5's `docs/bundle.schema.json` (copied 2026-10-18, issue #152); `tests/test_composer.py::test_vendored_schema_is_the_current_copy` pins which copy it is.

WHAT / SEAM: api/kobo_api/composer.py. `BundleSpec` (dataclass) → `compose(spec, dest)` writes the tree; `validate_agent_yaml(bundle_dir)` checks it against api/kobo_api/vendor/bundle.schema.json, a verbatim copy of daedalus `docs/bundle.schema.json` (never hand-edit; re-copy from daedalus). Called by RepoStep (steps.py) for composed agents only; connected agents bring their own repo.
OPS / FLOW: `compose` writes `Dockerfile` (single `FROM {runtime_image}` + `COPY bundle/ /bundle`), `bundle/agent.yaml`, `bundle/agent-card.json`, `bundle/persona.md`, `bundle/knowledge/self.md`, `bundle/knowledge/colleagues.md` (not when `colleague_mode` is `none`), `bundle/skills/<id>/**`, and `litestream.yml` + `entrypoint.sh` only when `memory_replica_bucket` is set. WireStep then adds `k8s/base/*` and edits `gojira.yaml` (steps.py); later lanes append `bundle/intake/*` (teach archive), tooling, and Slack transports.
agent.yaml shape (`_agent_yaml_data`): `model.id: ${AGENT_MODEL:-<id>}` (env override; the placeholder is substituted before schema validation), `max_tokens: 8192`, one a2a transport on :8080, `tools`, `memory: {personal: techne, home: /techne, revision: operator}`, `checkpoints: sqlite`, `approvals: {gates, escalation: {route: cli}}` (no `ceiling` since 2026-10-18: the runtime enforces only `ceiling.exec`, agora #55 item 7; agents composed earlier still carry `ceiling: {write: false}` until recomposed).
Switchboard-dependent parts (all gated on `spec.cabal_url` presence):
- a2a `auth`: `jwks_url = <cabal_url>/.well-known/jwks.json`, `issuer "cabal-core"`, `audience = <agent name>`. The agent accepts only switchboard-signed calls.
- `tools.provider: colleagues`, allow `colleagues.{list_colleagues,ask_colleague,remember}`, `token_env: CABAL_COLLEAGUE_TOKEN`; plus five explicit `github.` names via `broker_url` (`open_pr`, the one write, and the reads `list_prs`, `get_pr`, `list_releases`, `read_file`; never a `github.*` glob) and a `liminal` block via `liminal_url` when set. Team-guide archetype gets the colleague trio only.
- `skills.load` is appended to the allow list of every agent with skills, on every arm (no switchboard, team guide, any colleague mode; issue #137): daedalus 0.5.0 shows the skills index and offers the tool only when the allow list admits it, and older runtimes ignore a name no provider offers. self.md names the tool only for an agent with skills. A skill added after birth (skills.py `add_catalog_skill`, `save_local_skill`) runs `update_agent_yaml_skills_load` in the same commit, which appends `skills.load` unless an allow entry already matches it by fnmatch; a bundle whose agent.yaml can't be edited still gets the skill, with a warning.
- Colleague mode (`spec.colleague_mode`, the owner's per-agent setting, issue #131; row `Agent.colleague_mode`, NULL = `default`): `default` is the trio above and the consult-first doctrine in colleagues.md; `roster-only` drops `colleagues.ask_colleague` from the allow list and swaps the three doctrine paragraphs for `_ROSTER_ONLY_DOCTRINE` (say you don't know, name what you'd need, ask your human); `none` drops all three colleague tools and writes no colleagues.md. The provider block, a2a auth and sidecars stay in every mode: github/liminal ride the same colleague pass, and other agents may still ask this one. A change after birth goes through `update_agent_yaml_colleague_mode` (colleague_mode.py `commit_colleague_mode`, route `PUT /api/agents/{name}/colleague-mode`).
- `approvals.gates: []` when cabal is on; otherwise one `match "*" → plan_approval` gate.
INVARIANTS:
- Unconfigured cabal ⇒ byte-identical output to the pre-switchboard shape. WHY: existing repos must not churn on recompose.
- `colleague_mode` `default` ⇒ byte-identical agent.yaml and colleagues.md to the pre-#131 shape, pinned by digest in tests/test_colleague_mode.py; `update_agent_yaml_colleague_mode` never rewrites a file whose allow list already matches.
- Custom dumper forces flow style on the transport, tools and gates entries so each renders on ONE line; the `update_agent_yaml_*` editors (auth, tools, approvals_gates, memory_revision, max_tokens) edit by regex against that one-line shape and raise if not found. Never switch to a generic YAML re-dump here.
- Exactly one `FROM` line in the Dockerfile, even with litestream. WHY: `update_dockerfile_runtime_image` (runtime re-pin, used by runtime.py, tooling.py, intake.py, slack_setup.py) rewrites only the first `FROM` match, so with a second `FROM` the re-pin could hit the wrong stage. It returns the image it replaced (`None` when already current), and the incidental callers (tooling, intake, Slack) name such a re-pin in their commit message and the log via `repin_commit_note` (issue #140): the agents row is the authority, so a hand-edited `FROM` is put back, but never silently.
- `team` ≠ `group`: `team` is the skills-catalog axis (card `metadata.team`), `group` the ACL namespace (self.md only). Never conflate.
- agent-card.json `metadata.capability` starts `""`; HelloStep earns it and `commit_card_metadata` (metadata.py) writes it. The switchboard directory reads the card from the repo, so the repo is the source of truth for it.
- The card's `skills`, `description`, `version` and `metadata.runtime_image` are derived, never edited by hand (issue #147): `refresh_agent_card` reads them (and turns a legacy `capabilities: []` into `{}`) from `bundle/skills/`, `metadata.capability` (else persona.md's first sentence) and the Dockerfile `FROM` (`runtime_version` = the image tag, also for a `tag@digest` ref; a digest-only ref gives `sha256:<12 hex>`, issue #156). Every write that moves an input runs it in the same clone: skills.py's three mutations, `update_agent_card_metadata`, and `update_dockerfile_runtime_image` when it changes `FROM`. The skill and runtime routes then re-register the card with the switchboard (`_sync_directory_best_effort`, best effort, reported as `directory`); the fast-lane writers (intake, tooling upload/import, Slack wiring) take an `on_repin` hook that main.py fills with `_directory_resync`, called only when their commit moved `FROM`. That is how most agents' cards follow a room runtime upgrade, since most rows have no runtime of their own. An old card is corrected by the next such write, not at boot.
- Skill materialization rejects symlinks and paths escaping `dest` (`_materialize_skill` raises `ComposeError`).
- A write-capable tool must add its own approvals gate; nothing in `approvals` limits writes for it.
CONSUMERS: api/kobo_api/steps.py (RepoStep `compose`/`validate_agent_yaml`, `_self_md`/`_colleagues_md` for roster refresh), api/kobo_api/colleague_mode.py (`update_agent_yaml_colleague_mode`), api/kobo_api/runtime.py + tooling.py + intake.py + slack_setup.py (`update_dockerfile_runtime_image`), api/kobo_api/skills.py (`refresh_agent_card`, `update_agent_yaml_skills_load`), api/kobo_api/metadata.py (`update_agent_card_metadata`, `fallback_capability`), api/kobo_api/colleagues.py (`CABAL_COLLEAGUE_TOKEN_ENV`), api/tests/test_composer.py (incl. optional real-daedalus load via `pytest.importorskip("daedalus")`). Cross-repo: daedalus runtime loads this bundle at /bundle; gojira builds and deploys the repo.
GOTCHA: slack_setup.py `_update_agent_yaml_transports` round-trips agent.yaml through `yaml.safe_dump`, which rewrites the whole file in block style. After Slack is wired, the one-line shapes the `update_agent_yaml_*` regex editors need are gone. Those five editors have no production caller today (only tests/test_composer.py), so this is latent: don't reach for them on a Slack-wired agent without checking. `update_agent_yaml_colleague_mode` (the one with a production caller) parses the file and splices the whole tools section, so it handles the block-style file; tested on one.
