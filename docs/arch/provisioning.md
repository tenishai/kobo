# provisioning — the Create → running-agent step engine

WHAT / SEAM: `Step` Protocol (provisioner.py: `name`, `label`, `run(ctx: Ctx) -> str`); `Ctx(agent, session, config, clients, workdir)`. Engine: `run_pipeline` (daemon thread + `_Heartbeat` ticker), `_run_pipeline_body`, `_claim_step`, `reset_failed_steps`, `sweep_interrupted`, `pipeline_for(agent)`, `STEP_LABELS`. Steps live in steps.py; `StepSkipped` marks a best-effort step SKIPPED; `StepWaiting` parks a connected agent on its setup PR (status WAITING, resumed by `sweep_waiting`, which calls gojira's `sync_app` before `app_status` because without a GitHub webhook the platform's row never leaves `awaiting_pr`, issue #118). Since 2026-10-01 the process has a ROLE (roles.py, `KOBO_ROLE`): `all` (default, every test) launches pipelines inline from the routes; `api` only leaves the row PENDING with no heartbeat; `worker` runs `queue_loop` (`claim_queued`: one conditional UPDATE marks the first heartbeat, so two workers never run one agent; `queue_tick` launches up to 4), the sweeps and the nightly learnings pass, and `drain_pipelines` waits up to 25 minutes on shutdown so a roll never fails a build.
OPS / FLOW: `pipeline_for(agent)` picks by kind: composed `PIPELINE`, connected `CONNECTED_PIPELINE`, directory `DIRECTORY_PIPELINE` (#207: `ComposeDirectoryStep` writes `<directory_root>/<name>/` in one rename, `AvatarStep` keeps the picture in the room, `DirectoryStep` reads the card from the folder, `LoadStep` POSTs `directory_reload_url` or writes `.ready`). `destroy.destroy_steps_for(agent)` mirrors it: a directory agent's teardown is files, listing, record.
- composed `PIPELINE`: repo → avatar → onboard → access → wire → build → deploy → directory → hello.
- connected `CONNECTED_PIPELINE`: connect → avatar → onboard → access → wire(`ConnectedWireStep`, proposes a PR on branch `kobo/wire`) → build → deploy. No directory/hello: a connected agent is not in the colleague directory and nobody chats with it through the room. It does hold a colleague pass when the room has a gateway (2026-11-13), as the identity its own code trades for a gateway token.
- repo: compose bundle (composer.py) + create repo; with `bundle_registry` set (tenishai/kobo#434) the compose is the new shape (Dockerfile = FROM line alone, a dormant `{kind: slack, optional: true}` transport) and the step publishes the bundle (`delivery.publish`) before the first roll, since the pod pulls it at start; records `Agent.built_runtime_image` (the ref the composed Dockerfile's FROM carries, 2026-11-01) beside `repo_full_name` in the same commit, as `ComposeDirectoryStep` does for a directory agent; every later writer of that FROM line (the fast-lane re-pins in main.py, the runtime route) and the boot backfill in `kobo_api.runtime_truth` keep it current. onboard: gojira `create_app`, wait active. access (label Access since 2026-11-02): GSA `agent-<name>`, workload identity, `config.model_group` membership (or the Vertex role directly; neither when `models_gateway_url` is set, kobo#390: the gateway's identity holds it); and, with the permission service on and GitHub connected, `AccessStep._own_repository` calls `github_access.own_repository_default`: it writes the agent's GitHub child with its own repository as the set, files `github_repos_read` on it as the room actor and approves its own request (Read is the one level that stands until revoked, so the one that works as a default; the permission service lets the room actor decide exactly that request since bab 0.4.23, kobo#476, and kobo's `ROOM_ACTOR` `room@kobo` must equal the service's `room@<BAB_ROOM>`), then runs `gateway_lane.follow`; a rerun approves a room-raised Read request still waiting on an unchanged set and never asks twice; a set already picked stands; an older service refuses the decision (`DefaultWaits`) and the clause says the request waits for a reviewer; a refusal is a clause, never a failed step. wire: `_allow_held_lanes` puts the allow entries of every lane the agent already holds into `bundle/agent.yaml` in the wiring commit (`gateway_lane.sync_allow` skips an agent that is not Ready, and a later commit would be a second build); KSA + techne PVC manifests, register in kustomization.yaml, edit gojira.yaml (`service_account`; `VERTEXAI_PROJECT`/`VERTEXAI_LOCATION` only when the gateway is off, and with it on `_set_service_account_and_model_env` removes any stale copy so a reprovision of an older agent cleans them up, 2026-11-02; `secrets_from` gains `<name>-cabal` and, gateway on, `<name>-models`; with `bundle_registry` set, `delivery.wire_gojira_yaml` sets `bundle_image` (the node mounts the bundle image at /bundle as an image volume, pulled on every start with the node's credentials: no agent identity touches the registry) and adds `AGENT_NAME`/`MEMORY_REPLICA_BUCKET` to `env` and `<name>-slack`, `<name>-env` to `secrets_from_optional` (gojira renders `optional: true`); `ConnectedWireStep`'s PR body is `connected_wire_body(config)`), deliver colleague pass and the gateway key (`model_providers.deliver_models_key`, minted for every model an admin offers that the connected providers serve: `room_models.enabled_entries`, kobo#405; the compose names the agent's gateway model from `room_models.all_entries`, so a model hidden since the agent was made still composes) BEFORE push, reprovision, wait active. build: watch GH Actions run for the CURRENT head sha. deploy: rollout, then `DeployStep` verifies the live spec: the service account always, the two Vertex env names only when the gateway is off (a gateway agent's model access is the `<name>-models` Secret via envFrom, which `deploy_env_names` does not list). directory: cabal graduate (a no-op when the switchboard is off). hello: first contact via switchboard relay, or the direct path (`clients.agent.hello`) when the switchboard is off, then earns the capability line.
- Each step's row (`AgentStep`, unique (agent_id, name)) is persisted before the next runs. Route polls rows for the UI checklist; the request returns immediately.
- On READY (composed only): `sync_dispatch_pairs_best_effort` + `refresh_colleague_rosters` (provisioner.py ~l.380-410), both fail-soft. `refresh_colleague_rosters` returns the names of the viewers whose delivery missed (2026-10-29, issue #291); the READY flip ignores it, destroy-forget writes it into its note. The roster refresh skips a viewer whose `colleague_mode` is `none` (it has no colleagues.md) and renders a `roster-only` viewer's doc with that mode's doctrine. `_render_colleagues_md(viewer, roster, mode=...)` renders for a mode other than the row's: the colleague-mode route (main.py `set_colleague_mode`) uses it so it writes the row only after the push, never holding the agent's row lock across the clone and push (issue #133).
INVARIANTS:
- Order is load-bearing: each step reads state an earlier one recorded on `Agent` (`repo_full_name`, `gojira_app_id`, ...). directory must precede hello because agents compose LOCKED (only switchboard-signed calls accepted).
- `_claim_step` flips PENDING→RUNNING with one conditional UPDATE and checks rowcount. WHY: two replicas (or a retry racing a live run) must never execute the same step twice. Plain SQL, valid on SQLite and Postgres; do not replace with an in-process lock.
- A running pipeline beats `Agent.run_heartbeat_at` every 10s; `sweep_interrupted` fails only rows silent > 60s (`RUN_STALE_AFTER_S`), at boot and every 60s in every worker. In queue mode (`queue_mode=True`, any role but `all`) a never-started row is QUEUED, not dead, and is left alone. WHY: rolling updates start a new pod while the old one still provisions; failing all in-flight rows would kill live runs.
- Retry = `reset_failed_steps`: FAILED → PENDING, DONE/SKIPPED are skipped on re-run. If build or deploy failed (composed), wire and build are reset too (`REWIRE_AFTER_FAILED`/`REWIRE_RESETS`) so the rebuild is watched.
- WireStep: writing a manifest and registering it in kustomization.yaml are one act (gojira's generator preserves listed entries, it does not discover files; P0 lost a rollout to this). WireStep never completes without confirming gojira `active`, including the no-change resume path.
- repo/onboard steps re-check the outside world and refuse to adopt a same-named repo/app the row did not record (steps.py module docstring).
- BuildStep polls `runs_for_commit(head)` re-resolved each poll (gojira's setup PR auto-merges mid-provision), with one auto-rerun per watched sha for any non-success conclusion.
- A connected agent's build is not judged while its setup PR is open (kobo#475, 2026-11-13): gojira answers a provision call before its run marks the app `provisioning`, so `ConnectedWireStep` waits up to `CONNECTED_REPROVISION_GRACE_POLLS` reads for the row to leave the stale `active` before trusting it, and `BuildStep`, on a completed non-success run, asks the platform first (`_setup_pr_standing`): `awaiting_pr` raises the same `StepWaiting` as the wire step (`_setup_pr_waiting`, no rerun spent), `provisioning` keeps polling. WHY: the room's wiring commit fails gojira's manifest check until a person merges the setup PR, and every connect showed a failed build once.
- AvatarStep never fails the pipeline (raises `StepSkipped`).
- How Slack wakes a composed agent rides the room's own env keys in gojira.yaml and the row wins on a reprovision: `SLACK_WAKE_MODE` from `agents.slack_wake`, and (2026-11-13) `SLACK_WAKE_EMOJI` from `agents.slack_wake_emoji`, the emoji whose reaction also wakes it, and (2026-11-14) `SLACK_COMMAND_PUBLIC=on` from `agents.slack_command_public`, whether its slash command is answered in public channels it is not in. A NULL or false column writes no key. The wake route in `main.py` is what changes either after birth.
- A connected agent is wired like a composed one (2026-11-13, kobo#483): `add_room_wiring(data, agent, config)` adds to gojira.yaml a `data_mount` on `agent-<name>-data` at `/data` (kept as it is when the team declared one), `KOBO_DATA_DIR`, and, only when `gateway_identity_on(config)` (`liminal_url` and the switchboard), `<name>-cabal` in `secrets_from` with `KOBO_SWITCHBOARD_URL`/`KOBO_GATEWAY_URL`; with the model gateway, `<name>-models` and `KOBO_MODELS_URL`. `write_connected_storage` writes the claim as its own app-authored file `k8s/base/kobo-storage.yaml`. `deliver_connected_identity` mints the pass and the models key just before the wire request is OPENED, never on a Retry that finds it open (a mint revokes the pass before it). Every edit is additive, which is what lets `connected_wiring.offer` run the same function later over a file a team has changed. The four `KOBO_*` names are in `agent_env.RESERVED_KEYS` (and `ui/src/lib/dotenv.ts`). The contract a team's code reads is guide section `running-your-own-code`; `docs/examples/gateway_token.py` is the client side.
- Slack costs a connected repository no pull request after connect (2026-11-14): when `slack_app_possible(config, agent)` (the room has `slack_relay` and the agent is not headless), `_update_connected_gojira_yaml` also calls `name_slack_secret`, which puts `<name>-slack` under `secrets_from_optional`, so the agent starts without the Secret and reads it once an app exists. It is NOT in `add_room_wiring`: the catch-up `offer` must not open a request on an older repository for an app nobody asked for. How Slack wakes a connected agent travels in that Secret (`slack_setup.deliver_wake_settings`), not in gojira.yaml `env`, and a change is `delivery.restart_once_secret_carries(..., settings=...)`, which waits for the VALUES of those plain settings because a names-only wait cannot see a changed value. A container `env` entry hides an `envFrom` value, so `connected_wiring.follows_room` treats an older file that still sets a wake key as wired only while it agrees with the row; the first disagreement is one `kobo/slack` request (`hand_slack_to_room`) that removes the keys.
- After connect, `connected_wiring.keep(app)` runs on the worker's five-minute beat beside the gateway heal (`gateway_lane.heal_loop`, own try): `follow_through` compares the default branch's gojira.yaml with the `GOJIRA_CONTRACT` stamp in `.github/workflows/gojira-ci.yaml` (`contract_fingerprint`, the platform's own hash) and calls `gojira.reprovision` once per stale fingerprint, because a merged room pull request otherwise leaves the team's build refusing to deploy and nothing regenerates on a push; `offer` proposes the wiring on `kobo/wire` to a READY connected agent the first time it holds a lane and never merges it. Both remember in memory on `app.state` (`contract_asked`, `wiring_settled`), so a restart asks once more, which is harmless. `connected_wiring.state` feeds `wiring` on `GET /api/agents/{name}/access`.
- ConnectedWireStep tells "wiring to propose" from "already wired" by the *meaning* of its three files, not their bytes: `_register_resources` and `_update_connected_gojira_yaml` return without writing when the parsed document is unchanged, so a file formatted the generator's way (comments, two-space lists) is not a change. Re-dumping it was the wire loop with gojira's regeneration (#123 item 11, PR #151).
- Engine-level failures (workdir, commit, missing row) mark the agent FAILED directly; they have no step boundary to resume from.
CONSUMERS: api/kobo_api/main.py (`POST /api/agents`, `/api/agents/connect`, `/api/agents/{name}/retry` call `run_pipeline(..., steps=pipeline_for(agent))` in role `all`, and only set PENDING otherwise; `build_default_app` calls `sweep_interrupted`, `_room_lifespan` runs `interrupted_sweep_loop`); api/kobo_api/mcp/tools/write.py (`kobo_create_agent` calls the create route function directly); tests/test_integrity.py (toy steps, the two-real-process claim test, resume and sweep, end-to-end with fakes), tests/test_incidents.py (the onboard-conflict and build-sha incidents), tests/test_access.py (roster visibility).
API: `run_pipeline(session_factory, agent_id, *, config, clients, steps) -> Thread`; `reset_failed_steps(session, agent_id)`; `sweep_interrupted(session_factory, *, now=None, queue_mode=False) -> int`; `claim_queued(session_factory, *, limit, now) -> list[int]`; `queue_tick(...) -> int`; `drain_pipelines(app, *, timeout_s) -> int`; `pipeline_for(agent)`; `STEP_LABELS` (UI checklist vocabulary, union of both lists).
