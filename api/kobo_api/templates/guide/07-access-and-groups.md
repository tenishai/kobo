# Access and groups
<!-- summary: Who sees an agent, adding an owner, what the agent may reach at each vendor, where agent to agent requests live, and moving an agent. -->

An agent belongs to one group, chosen when it was created. Everyone in that group sees the agent on the dashboard and can chat with it. Its owner and the room's operators always see it. Nobody else does.

The **shared** group is the exception: an agent filed there is visible to everyone in the company.

## The Access tab

You see this tab on agents you own or manage. It opens on **What this agent can reach**: only the vendors the room has connected, each with its logo, and under each vendor what the agent already holds there. A vendor nobody has connected is not listed; as admins connect more under Integrations, more appear. When nothing is connected yet the tab says so and names Integrations, where a kobo admin adds one. One line under the heading says which identity the agent runs as. Who may see or manage the agent is not here but under **Owners** in the header; which agents it may talk to is under **Agent to agent** on the Harness tab.

**Owners.** The button in the agent's header, beside **Edit details**, with a count. It is who can see and manage this agent besides its owner and the room's operators. Press it, then **Add person**, type an address (the room offers matches from the directory) and pick a role. **Can see** opens the agent and chats with it. **Can manage** also edits its skills, tooling, Slack, secrets and permission requests; it cannot destroy the agent, and it cannot add or remove people here. Adding someone again with the other role changes their role. **Remove** takes the access back.

**Agent to agent.** Which agents from other teams this one may ask for help, and who has asked to reach it, live on the Harness tab under **Agent to agent**. See "The harness" and "Agents talking to agents".

**What this agent can reach.** What the agent may do at each vendor the room has connected, when the room's permission service is on. The agent holds no standing credential: when a task needs one, it borrows an hour of access scoped to exactly the permissions it holds, and the vendor's own audit trail names the agent. Under each vendor is what it holds there, by service and account, with the tier and when it expires (read permissions stand until revoked; write permissions expire and are asked for again). For GitHub the line under the vendor's name is about this agent, how many repositories it may reach; other vendors' name and logo stand alone. Room admins see **Revoke now** on each row. The first permission approved on a vendor also puts that vendor's tools in front of the agent: its files change once and it restarts once, and from then on the gateway decides tool by tool from what it holds; a permission revoked takes its tools away the same way.

To ask for more, pick the vendor in the list, then the level, then **Confirm**. AWS, Google Cloud and Azure are connected one account, project or subscription at a time, so after the vendor comes the account; Datadog, Atlassian and the like are one connection each and open straight on their levels. Only accounts a room admin has connected on Admin, Integrations are listed. Find the service you need with the search box, tick it, and press **Confirm**. Read means configuration and listings, never the data a service holds. A service the connection does not allow is greyed with the reason, not hidden. Requests go to the room's reviewers in Admin, Review; until they decide, the row says "waiting for review".

**GitHub** is asked for in two steps. First pick the repositories: type part of a name and the picker shows the best matches, with the ones already picked kept in view, out of every repository the room's GitHub app can see (it says how many that is); tick the ones this agent should work in. One agent has one repository set, and every GitHub permission it holds applies to that set; changing the set is a new request, and a token already out keeps the old set until its hour runs out. Then pick a level: **Read** (code, issues, pull requests, checks and workflow runs), **Review pull requests** (Read, plus reviewing and commenting on pull requests), or **Open pull requests** (Review, plus branches, commits and pull requests of its own). An agent can never approve a pull request it opened; that is the vendor's rule. The reviewer in Admin, Review sees the repository set beside the request. The room's own GitHub app is never granted to an agent: it is what the room mints each agent's token from.

## When you can see an agent but do not own it

Instead of an Access tab you get **Request colleague access**: pick one of your own agents and ask the owner to let it talk to this one. The owner sees the request under **Agent to agent** on their agent's Harness tab.

## Moving an agent

Only an operator can move an agent to a different group. Ask one if an agent was created under the wrong group. Everything else about the agent stays as it is.

## Readers

Some groups are configured as readers. Members see every agent in the room and can change none of them. This is for people whose job is to know what exists.

## Your account menu

The bottom of the left rail is your account menu: press your email to open it. It shows who you are signed in as and **Log out** when the room's sign-in has a sign-out path. Room admins also see **Admin** there once the room's admin panel is turned on; nobody else sees the entry, and the page itself refuses anyone who is not an admin.

The admin panel has eight pages. **Overview** is one row per page with the number that matters. **Services** lists what the room runs on and whether each answers; its one button re-reads the org config and asks before it does. The room keeps its own house: each night it retires switchboard directory entries that no longer have an agent behind them, and the audit log says what it retired. **Integrations** is one table of the room's own connections, nothing an agent holds: the vendors agents can reach, one connection each, and two rows that are always there for the services the room itself uses, **Slack** (the config tokens it creates agents' Slack apps with) and **GitHub** (the app the room acts with: agent repositories, skill and tooling pull requests). On a fresh room both read **Not set up**, and every agent's Slack tab is a greyed box asking a kobo admin to add the integration. An admin pastes each once with **Set up**; agents can use it at once, no restart. A value an older install's deployment config carries reads Connected too, marked set in the deployment config, and **Replace** moves it into the room, where the room's value wins; **Replace** swaps what was pasted and **Remove** (which asks first) takes it back. A fresh room has nothing baked in: an admin pastes both here. **Add integration** adds a vendor. AWS connects as an organization. Pick how you create roles (Terraform, CloudFormation or by hand) and the page shows only that method: one hub role in the organization's management account, trusting the room's identity and allowed only to assume each member account's role, list the accounts and read the bill; and one spoke role for every member account, from one template with the organization's one external id, so a StackSet puts it everywhere at once. Paste the hub's ARN; the room checks it with AWS, saves, and then checks every account through the hub. Accounts that carry the spoke role connect themselves with the read permissions agents may ask for; the rest show under the organization as **No role yet**. **Check accounts** on the organization runs that check again after you deploy the role to more accounts. A second organization is a second row, never an assume across organizations. Datadog, when the permission service is on, connects through it: in Datadog make a service account for the room with a role that holds service_account_write and every Datadog read permission, one API key, and one application key owned by that service account and scoped to service_account_write (the management key); paste the service account id and the two keys, the room checks them by minting and removing a probe key, and from then on each agent that is granted Datadog borrows its own short-lived application key, scoped to exactly what it was granted and removed when the hour ends. Connecting Datadog also adds Datadog's MCP server to the gateway at once, so an agent granted Datadog uses those tools with the same borrowed key; a room whose gateway predates that lane gets a pull request on the gateway's config repository instead, and the row reads Pending until it merges. Approving an agent's first Datadog permission opens its lane on the gateway too, so the permission is the only thing anyone grants. **Agent connections** answers which agents reach which vendors, with what, right now: one card per agent with its portrait, name, team and status, inside it one row per vendor with its logo, then what the agent holds there (the permission, its tier, when it expires, who granted it) and what it is borrowing at this moment (the permissions, the task, when it was issued, when it ends, through what). An agent's own GitHub repository set shows here too, with its repositories. **Revoke** on a held row takes the permission back the same way the agent's Access tab does, and the open sessions end with it. A search box narrows the cards by agent, vendor or repository, and an agent that holds nothing is still a card, so the page is the whole truth. When the permission service is off this page is **Connections** instead, which gives an agent a lane to a vendor. **Review** is where permission requests wait when the permission service is on: a **Borrowed now** table of the credentials out at this moment, then the requests; tick rows, **Approve**, or **Deny** with a reason; **Sync agents** tells the service which agents exist. A request to ask another team's agent is in the same list, with the asked agent as the account and **ask** as its one permission; approving it pairs the two agents on the switchboard at once. **Roles** records what a group should be allowed to do; the room shows roles but does not enforce them yet. **People** shows who runs the room and who is asking for a group. **Audit** is the room's log of what people, the room and agents did: creating, teaching, changing a model, adding a skill, connecting Slack, asking for or approving access, and every change made from this panel, one sentence per row, newest first, with where it came from and whether it has landed. Search it, narrow it by actor, kind of action, agent, outcome or dates, load older rows as you go, and export what you are looking at as CSV or JSON. An agent's page links to the log filtered to that agent. The log has two tabs: **People** is what people and the room did, and **Agents** is what agents did with their connections, each time one borrowed access, was refused it or could not get it, read live from the permission service with its own export. Rows are kept for the room's retention window, thirty days unless the room is set otherwise. GitHub is also a vendor agents can be granted: **Add GitHub** on the same page reuses the room's app (or one you paste), and the room then mints each granted agent a short-lived installation token, narrowed to its level and to the repository set its owner picked on the agent's Access tab. Connecting GitHub adds two of its MCP server targets to the gateway, one read-only and one that writes; an agent reaches the second only at the Review pull requests level and creates branches and pull requests only at Open pull requests, and merging and deleting are refused at every level. The app must hold every permission agents may be granted (metadata, contents, issues, pull requests, actions and checks read; pull requests and contents write) or the vendor refuses the token.
