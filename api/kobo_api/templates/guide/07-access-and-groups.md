# Access and groups
<!-- summary: Who sees an agent, adding an owner, what the agent may reach at each vendor, where agent to agent requests live, and moving an agent. -->

An agent belongs to one group, chosen when it was created. Everyone in that group sees the agent on the dashboard and can chat with it. Its owner and the room's operators always see it. Nobody else does.

The **shared** group is the exception: an agent filed there is visible to everyone in the company.

## The Access tab

You see this tab on agents you own or manage. It opens on **What this agent can reach**: only the vendors the room has connected, one row each with its logo and one line on where things stand there ("2 held, 1 waiting for review", "Nothing held yet", or for Slack whether it is live). A row opens on click to show what the agent holds there and the picker to ask for more; one row is open at a time, and the row you opened last stays open while you are in the room. Vendors with something held or waiting come first, Slack last. When the agent's last attempt to use a vendor failed, that row says so with the reason, so you know why it told you its credential did not resolve; the line clears once the agent gets a credential there again. A vendor nobody has connected is not listed; as admins connect more under Integrations, more appear. When nothing is connected yet the tab says so and names Integrations, where a kobo admin adds one. One line under the heading says which identity the agent runs as. Who may see or manage the agent is not here but under **Owners** in the header; which agents it may talk to is under **Agent to agent** on the Harness tab.

**Owners.** The button in the agent's header, beside **Edit details**, with a count. It is who can see and manage this agent besides its owner and the room's operators. Press it, then **Add person**, type an address (the room offers matches from the directory) and pick a role. **Can see** opens the agent and chats with it. **Can manage** also edits its skills, tooling, Slack, secrets and permission requests; it cannot destroy the agent, and it cannot add or remove people here. Adding someone again with the other role changes their role. **Remove** takes the access back.

**Agent to agent.** Which agents from other teams this one may ask for help, and who has asked to reach it, live on the Harness tab under **Agent to agent**. See "The harness" and "Agents talking to agents".

**What this agent can reach.** What the agent may do at each vendor the room has connected, when the room's permission service is on. The agent holds no standing credential: when a task needs one, it borrows an hour of access scoped to exactly the permissions it holds, and the vendor's own audit trail names the agent. Under each vendor is what it holds there, by service and account, with the tier and when it expires (read permissions stand until revoked; write permissions expire and are asked for again). For GitHub the line under the vendor's name is about this agent, how many repositories it may reach; other vendors' name and logo stand alone. Room admins see **Revoke now** on each row. The first permission approved on a vendor also puts that vendor's tools in front of the agent: its files change once and it restarts once, and from then on the gateway decides tool by tool from what it holds; a permission revoked takes its tools away the same way.

To ask for more, pick the vendor in the list, then the level, then **Confirm**. AWS, Google Cloud and Azure are connected one account, project or subscription at a time, so after the vendor comes the account; Datadog, Atlassian and the like are one connection each and open straight on their levels. Atlassian's Write issues level (create, edit, comment on and move Jira issues) is there only when a room admin connected Atlassian for reading and writing; it is granted for thirty days at a time. Only accounts a room admin has connected on Admin, Integrations are listed. Find the service you need with the search box, tick it, and press **Confirm**. Read means configuration and listings, never the data a service holds. A service the connection does not allow is greyed with the reason, not hidden. Requests go to the room's reviewers in Admin, Review; until they decide, the row says "waiting for review".

**GitHub** is asked for in two steps. First pick the repositories: type part of a name and the picker shows the best matches, with the ones already picked kept in view, out of every repository the room's GitHub app can see (it says how many that is); tick the ones this agent should work in. One agent has one repository set, and every GitHub permission it holds applies to that set; changing the set is a new request, and a token already out keeps the old set until its hour runs out. Then pick a level: **Read** (code, issues, pull requests, checks and workflow runs), **Review pull requests** (Read, plus reviewing and commenting on pull requests), or **Open pull requests** (Review, plus branches, commits and pull requests of its own). An agent can never approve a pull request it opened; that is the vendor's rule. GitHub shows the room's app as the author of everything an agent writes, so the room signs for it: every comment, review and pull request an agent makes opens with the agent's name and its portrait, served from the agent's own repository to anyone who can see it, and an agent names the branches it creates after itself. The reviewer in Admin, Review sees the repository set beside the request. The room's own GitHub app is never granted to an agent: it is what the room mints each agent's token from. Jira works the same way: **Write issues** on an Atlassian connection lets an agent open issues and comment through tools that put its name in the summary and a signature at the top, while the room's Atlassian account is the author.

## When you can see an agent but do not own it

Instead of an Access tab you get **Request colleague access**: pick one of your own agents and ask the owner to let it talk to this one. The owner sees the request under **Agent to agent** on their agent's Harness tab.

## Moving an agent

Only an operator can move an agent to a different group. Ask one if an agent was created under the wrong group. Everything else about the agent stays as it is.

## Readers

Some groups are configured as readers. Members see every agent in the room and can change none of them. This is for people whose job is to know what exists.

## Your account menu

The bottom of the left rail is your account menu: press your email to open it. It shows who you are signed in as and **Log out** when the room's sign-in has a sign-out path. Room admins also see **Admin** there once the room's admin panel is turned on; nobody else sees the entry, and the page itself refuses anyone who is not an admin.

The admin panel has nine pages. **Overview** is one row per page with the number that matters, and when the permission service is on it carries an **Agent connections** card counting how many agents hold access right now. **Services** lists what the room runs on and whether each answers; its one button re-reads the org config and asks before it does. Its **Models** row is the room's model gateway: off when the room is not set to use one (agents then reach models with their own identity), **Not answering** when it does not reply, and on with how many clouds serve models, how many models can be picked and which one a new agent gets by default. A fresh room with the gateway on has no models until a cloud with models is connected under Integrations, and nobody can create an agent until one is. The room keeps its own house: each night it retires switchboard directory entries that no longer have an agent behind them, and the audit log says what it retired. **Integrations** is one table of the room's own connections, nothing an agent holds: the vendors agents can reach, one connection each, and one kind of row. A fresh room shows an empty table and **Add integration**; nothing is baked in. Two of the vendors are also the room's own: **Slack**, whose connection is the app configuration token pair the room creates agents' Slack apps with, and **GitHub**, whose connection is the app the room acts with (agent repositories, skill and tooling pull requests). Add them like any vendor: pick Slack and paste the pair, or pick GitHub and paste the app id, the installation id and the private key; agents can use them at once, no restart. Until Slack is added, every agent's Slack row is a greyed box asking a kobo admin to add the Slack connection. A value an older install's deployment config carries reads Connected too, marked set in the deployment config, and **Replace** moves it into the room, where the room's value wins; on a row the room holds, **Replace** swaps what was pasted and **Remove** (which asks first) takes it back. AWS connects as an organization. Pick how you create roles (Terraform, CloudFormation or by hand) and the page shows only that method: one hub role in the organization's management account, trusting the room's identity and allowed only to assume each member account's role, list the accounts and read the bill; and one spoke role for every member account, from one template with the organization's one external id, so a StackSet puts it everywhere at once. Paste the hub's ARN; the room checks it with AWS, saves, and then checks every account through the hub. Accounts that carry the spoke role connect themselves with the read permissions agents may ask for; the rest show under the organization as **No role yet**. **Check accounts** on the organization runs that check again after you deploy the role to more accounts. A second organization is a second row, never an assume across organizations. One account can also connect on its own: pick **One account** at the top of the AWS sheet, and the role is one the room assumes directly, named by you. Tick **Use this account's Bedrock models in the room** and give a region (us-east-1 unless you say otherwise) to make that account the room's model provider on AWS: the page adds the Bedrock permissions block to the role's snippets (the trust is unchanged), the row reads "Models: Bedrock, us-east-1", and the models the room's list names on AWS appear in New agent and Change model tagged AWS. The room does not list the account's models at connect; the first time an agent uses one is the check with AWS. Removing the row takes its models off the lists. **Bedrock models only** is the third choice on the AWS sheet, for a role that holds the Bedrock permissions and nothing else: the account serves models to the room, its row reads "Models only: Bedrock, us-east-1", and agents are granted nothing there, so no agent's Access tab offers it. Google Cloud connects as an organization, granted once; one project is the other choice. Pick Google Cloud, keep **An organization** (or choose **A project**), and the page shows the room's identity (an email) and the roles to grant it there, three ways: gcloud commands, Terraform, or the list to add in the console. Grant them once on the organization, type its id (organizations/number) and press Connect; every project under it the identity can read connects by itself with the read permissions agents may ask for, and the rest show as **Not granted yet** until you grant them and press **Check projects**. A single project is typed by its id instead, and the room checks it can read it as that identity; nothing is saved until Google Cloud agrees. On either sheet, tick **Include this project's Vertex AI models in the room**, name the Vertex AI project (on a project sheet it is the project itself unless you name another) and give a location (global unless you say otherwise, or a region such as us-east5): the room lists that project's models there before saving, refuses the connect when it cannot, and the row reads "Models: Vertex AI, my-vertex-project, global"; the project's own row under the organization says the same. With the model gateway on, connecting puts those models on the gateway at once, and they appear in the New agent and Change model lists, tagged GCP, once a room admin ticks them under **Models**; removing the row takes exactly its models off again. If the gateway did not take them, the row stays connected and its line says so. **Self-hosted models** is the one kind that is only models: models you run yourself, on your own machines or clusters, at an address you give the room. Pick it, name the endpoint (a room may hold several, one row each), give the base address the server answers /v1/models at (the room adds /v1 when it is missing), a key if the server wants one, the models it serves one per line (a name, or name = label), and, if a model needs them, request options sent with every call, such as turning a model's thinking off so a short reply is not spent on it. On connect the room lists the models at the address and asks each one you named for a short answer; the row connects as long as one answers, reads how many do ("2 of 3 models answer") and names the ones that did not with the server's own words, and only the answering ones join the New agent and Change model lists, under the row's name. **Check models** on the row asks again, after you fix or retire an entry. Removing the row takes its models off the lists and forgets the key. **Models** is where a room admin chooses what New agent and Change model offer: one section per connected cloud or self-hosted endpoint, with its tag (GCP, AWS, Azure, Self-hosted), its name, and the chat models it has right now, read from the cloud itself; tick a model to offer it, untick it to hide it, and an unticked one reads **Hidden from New agent**. The room's own list seeds the first ticks with its price names and tiers; after that this page is the choice, and every tick is in the audit log. Until a cloud or an endpoint is connected the page says so and shows which are not connected. Datadog, when the permission service is on, connects through it: in Datadog make a service account for the room with a role that holds service_account_write and every Datadog read permission, one API key, and one application key owned by that service account and scoped to service_account_write (the management key); paste the service account id and the two keys, the room checks them by minting and removing a probe key, and from then on each agent that is granted Datadog borrows its own short-lived application key, scoped to exactly what it was granted and removed when the hour ends. Connecting Datadog also adds Datadog's MCP server to the gateway at once, so an agent granted Datadog uses those tools with the same borrowed key; a room whose gateway predates that lane gets a pull request on the gateway's config repository instead, and the row reads Pending until it merges. Approving an agent's first Datadog permission opens its lane on the gateway too, so the permission is the only thing anyone grants. **Agent connections** answers which agents reach which vendors, with what, right now: one card per agent with its portrait, name, team and status, inside it one row per vendor with its logo, then what the agent holds there (the permission, its tier, when it expires, who granted it) and what it is borrowing at this moment (the permissions, the task, when it was issued, when it ends, through what). An agent's own GitHub repository set shows here too, with its repositories. **Revoke** on a held row takes the permission back the same way the agent's Access tab does, and the open sessions end with it. A search box narrows the cards by agent, vendor or repository, and an agent that holds nothing is still a card, so the page is the whole truth. When the permission service is off this page is **Connections** instead, which gives an agent a lane to a vendor. **Review** is where permission requests wait when the permission service is on: a **Borrowed now** table of the credentials out at this moment, then the requests; tick rows, **Approve**, or **Deny** with a reason; **Sync agents** tells the service which agents exist. A request to ask another team's agent is in the same list, with the asked agent as the account and **ask** as its one permission; approving it pairs the two agents on the switchboard at once. **Roles** records what a group should be allowed to do; the room shows roles but does not enforce them yet. **People** shows who runs the room and who is asking for a group. **Audit** is the room's log of what people, the room and agents did: creating, teaching, changing a model, adding a skill, connecting Slack, asking for or approving access, and every change made from this panel, one sentence per row, newest first, with where it came from and whether it has landed. Search it, narrow it by actor, kind of action, agent, outcome or dates, load older rows as you go, and export what you are looking at as CSV or JSON. An agent's page links to the log filtered to that agent. The log has two tabs: **People** is what people and the room did, and **Agents** is what agents did with their connections, each time one borrowed access, was refused it or could not get it, read live from the permission service with its own export. Rows are kept for the room's retention window, thirty days unless the room is set otherwise. The GitHub connection is also what agents are granted: with the permission service on, the room mints each granted agent a short-lived installation token from the same app, narrowed to its level and to the repository set its owner picked on the agent's Access tab. Connecting GitHub adds two of its MCP server targets to the gateway, one read-only and one that writes; an agent reaches the second only at the Review pull requests level and creates branches and pull requests only at Open pull requests, and merging and deleting are refused at every level. The app must hold every permission agents may be granted (metadata, contents, issues, pull requests, actions and checks read; pull requests and contents write) or the vendor refuses the token.
